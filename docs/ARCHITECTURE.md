# Архитектура Offline WebView

## Цель

Обёртка над одним доверенным сайтом. При наличии сети WebView получает свежие
ресурсы. Успешные кэшируемые GET-ответы сохраняются во внутреннее хранилище.
Если запрос завершается сетевой ошибкой, WebView получает последнюю целостную
копию того же URL.

## Компоненты

1. `MainActivity` — экран, жизненный цикл WebView, кнопка «назад».
2. `OfflineWebViewClient` — маршрутизация навигации и перехват запросов.
3. `CachingRequestInterceptor` — политика network-first и преобразование ответа.
4. `FileResponseCache` — атомарная запись тела и метаданных, поиск, LRU-очистка.
5. `AppConfig`/`BuildConfig` — стартовый URL, разрешённый хост, лимит кэша.
6. GitHub Actions — тест, сборка debug APK, публикация artifact.

## Поток запроса

```text
WebView GET
  ├─ другой хост / другой метод → штатная сеть WebView
  └─ разрешённый хост
       ├─ HTTP 2xx/3xx → вернуть ответ и атомарно сохранить, если разрешено
       ├─ HTTP 304 → вернуть сохранённое тело
       └─ сеть недоступна/таймаут → вернуть сохранённый ответ
                                    или штатную ошибку, если записи нет
```

## Ключ кэша и метаданные

Ключ — SHA-256 полного нормализованного URL. Для записи хранятся:

- тело ответа;
- MIME type и charset;
- HTTP status/reason;
- безопасные response headers;
- `ETag`, `Last-Modified`, время сохранения и последнего доступа.

Запись сначала создаётся во временных файлах, затем заменяет текущую. Поэтому
аварийное завершение не оставляет WebView частично записанный ресурс.

## Стратегия обновления

Первая версия использует network-first: это даёт свежий контент и простой
предсказуемый офлайн-режим. Если в кэше есть `ETag` или `Last-Modified`, клиент
отправляет условный запрос. Ответ `304` обновляет время доступа без повторной
загрузки тела.

Следующий этап для SPA — серверный `asset-manifest.json` с номером версии и
хэшами. Приложение скачивает новую версию в отдельное поколение, проверяет все
файлы и только затем атомарно переключает активное поколение. Это исключает
смесь старых HTML и новых JS.

## Серверный контракт

Рекомендуется:

- неизменяемые ассеты с хэшем в имени:
  `Cache-Control: public, max-age=31536000, immutable`;
- `index.html` и manifest:
  `Cache-Control: no-cache` плюс `ETag`;
- персональные/секретные ответы:
  `Cache-Control: no-store`;
- корректные `Content-Type`, `Content-Encoding`, `ETag`, `Last-Modified`;
- один зарезервированный префикс, например `/app/`, для офлайн-контента.

## Риски, которые проверяем отдельно

- OAuth/SSO, cookies `SameSite`, redirects и ответы авторизованных API;
- Service Worker сайта и его взаимодействие с нативным кэшем;
- CORS/CSP, mixed content, certificate errors;
- видео/range requests, WebSocket, `blob:` и большие файлы;
- согласованность SPA-релиза и поведение при первом запуске без сети;
- очистка приватных данных при logout.

## Этапы реализации

1. Каркас приложения, безопасные настройки WebView, удалённая debug-сборка.
2. Файловый кэш, network-first, условные запросы, лимит размера.
3. Unit-тесты политики и интеграционные тесты с локальным HTTP-сервером.
4. Экран состояния: online/offline, объём и очистка кэша.
5. Версионированный manifest и атомарное предварительное обновление SPA.
6. Release signing, защищённые GitHub Secrets и release APK/AAB.
